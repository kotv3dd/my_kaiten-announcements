# Правила написания анонсов Кайтен

Документ описывает структуру, обязательные блоки и стилевые требования к анонсам новых функций для Справочного центра Кайтена. Правила выведены из эталонных анонсов и служат чек-листом для автора и редактора.

---

## 1. Структура анонса

Анонс всегда строится по единому каркасу. Порядок блоков фиксирован.

### 1.1. Заголовок

- Емко и коротко передает суть фичи в понятном пользователю формате.
- Формулируется от лица продукта в двух допустимых вариантах:
  - **Название фичи как объект**: «Брендирование Справочного центра», «Выбор вида карточек для каждого пространства».
  - **Действие от команды** (глагол в прошедшем времени, «мы» подразумевается): «Обновили управление External Webhooks», «Кратно подняли пропускную способность нашего API для интеграций».
- Без маркетингового пафоса, без восклицательных знаков, без кликбейта. Заголовок = что произошло, а не «как это круто».
- Термины продукта пишутся так, как приняты в интерфейсе (External Webhooks — латиницей, если так в продукте).

### 1.2. Первый абзац (превью-описание)

Выводится в превью карточки анонса, поэтому несет основную нагрузку.

- Начинается со слова **«Теперь…»** или с глагола-действия («Обновили…», «Лимит запросов вырос…»). Это сразу сообщает, что изменилось.
- Содержит: **что** пользователь теперь может сделать → **какую пользу** получит → **как качественно меняется** работа с продуктом.
- Длина: 2–4 предложения. Первое — суть, следующие — контекст пользы.
- Ключевые сущности оформляются **ссылками на статьи Базы знаний** прямо в тексте (например, «[пространства]», «[Справочный центр]», «[API Kaiten]»).
- Пишется так, чтобы быть понятным в отрыве от остального текста — читатель в ленте видит только этот абзац.

**Пример структуры:** «Теперь для каждого [пространства] можно выбрать свой вид карточек: в одном использовать компактный, а в другом — полный или настроить собственный. [Далее — что еще изменилось]».

### 1.3. Первое изображение (превью-картинка)

- Идет **сразу после первого абзаца**.
- Визуально отражает контекст фичи: скриншот нового интерфейса, экрана настроек или ключевого действия.
- Используется как обложка анонса в превью — должна считываться даже в мелком размере.

### 1.4. Блок доступности

Идет **сразу под первым изображением**, до горизонтального разделителя. Короткие фразы без «воды».

Указывается:
- **Тип поставки**: доступна во всех версиях / только облачным клиентам / только в серверной поставке.
- **Версия серверной поставки**, если применимо: «В серверной поставке начиная с версии 58.52.5».
- **Тариф / модуль**, если есть ограничения: «Обновление доступно только для аккаунтов с модулем "Группы пользователей"».
- **Стадия**, если фича не финальная: «Функциональность находится в стадии Beta».
- **Условие появления**, если требуется действие пользователя: «Новый интерфейс появится после обновления приложения до последней версии».

**Типовые формулировки:**
- «Функция уже доступна облачным клиентам Kaiten. В серверной поставке начиная с версии XX.XX.X».
- «Функциональность находится в стадии Beta. Доступна в облачной версии Kaiten».

### 1.5. Горизонтальный разделитель

После блока доступности ставится `---`. Он визуально отделяет превью-часть (заголовок + первый абзац + картинка + доступность) от подробного описания.

### 1.6. Основная часть

Подробное раскрытие фичи. Обязательно отвечает на вопросы: **зачем это нужно**, **что именно изменилось**, **как этим пользоваться**.

Рекомендуемые смысловые блоки (набор гибкий, подбирается под фичу):

- **Контекст / проблема «раньше»**. Начинается с описания, как было до обновления и почему это было неудобно: «Раньше, когда вы выбирали вид карточек, он применялся ко всем пространствам. Это было неудобно, потому что…». Этот приём показывает ценность через контраст.
- **«Что такое …»** — короткое определение, если фича опирается на понятие, которое пользователь может не знать (например, «Что такое дополнение»).
- **«Что изменилось»** — суть нововведения после проблемного контекста.
- **Сценарии и кейсы использования** — список задач, которые фича решает: «С новым лимитом вы можете: синхронизировать задачи с CRM… обрабатывать поток заявок… подключать ИИ-инструменты…».
- **Пошаговая инструкция** — как начать пользоваться. Всегда нумерованный список, каждый шаг — одно действие. Названия кнопок и разделов выделяются **жирным** или в «кавычках-ёлочках». После ключевых шагов — поясняющий скриншот.
- **Предупреждения и нюансы** — когда система покажет подтверждение, что нельзя откатить, как сбросить настройки. Оформляются отдельным абзацем рядом с соответствующим шагом.

### 1.7. Блок «Полезные ссылки» / «Полезные материалы»

- Обязательный финальный смысловой блок.
- Заголовок третьего уровня: «Полезные ссылки» (или «Полезные материалы» для технических анонсов).
- Маркированный список ссылок на смежные статьи Базы знаний и документацию, раскрывающие контекст глубже.
- Обычно 2–4 ссылки: базовое понятие + инструкция по смежной функции + документация для разработчиков (для технических фич).

## 2. Работа с изображениями

- **Первое изображение** — превью, идет после первого абзаца (см. 1.3).
- Скриншоты расставляются **сразу после шага или абзаца**, который они иллюстрируют, а не пачкой в конце.
- Под скриншотами при необходимости даются **курсивные подписи**, поясняющие, что на них: «*Боковая панель с видами карточек. Активный вид выделен.*», «*Категории видов карточек*».
- Каждый значимый шаг инструкции сопровождается своим скриншотом.
- Изображения показывают реальный интерфейс продукта, а не абстрактные иллюстрации.

## 3. Ссылки

- Ключевые термины и сущности превращаются в ссылки **при первом упоминании** прямо в теле текста.
- Ссылки ведут на статьи Базы знаний, портал разработчиков (developers.kaiten.ru) или смежные анонсы.
- Для перехода к подробной инструкции используется формат со стрелкой: «Подробнее о том, как создать Справочный центр, [читайте в статье →]».
- Финальный блок «Полезные ссылки» дублирует и дополняет самые важные ссылки списком.

## 4. Редполитика и TOV

Анонс пишется в едином голосе Кайтена: спокойном, дружелюбном, помогающем, без агрессивного маркетинга.

### Что делать

- **Обращение на «вы»** (со строчной), уважительно и на равных: «вы можете», «откройте настройки».
- **«Мы» — от лица команды продукта**, подразумевается в глаголах: «Обновили», «Подняли», «Собрали в новом разделе».
- **Короткие предложения**, прямой порядок слов, без канцелярита.
- **Активный залог** вместо пассивного: «Kaiten покажет предупреждение», а не «будет показано предупреждение».
- **Фокус на пользе для пользователя**, а не на факте разработки: не «мы реализовали», а «теперь вы можете».
- **Приём «Раньше → Теперь»** для демонстрации ценности изменения.
- **Точные названия** элементов интерфейса, кнопок и разделов — так, как они выглядят в продукте.
- **Технические детали** (форматы файлов, размеры, лимиты) приводятся конкретно: «Формат PNG, 480×192 px, до 2 МБ».

### Написание названия продукта

- В тексте название продукта пишется кириллицей — **«Кайтен»** — согласно редполитике.
- В устойчивых технических конструкциях, названиях разделов интерфейса и API сохраняется оригинальное написание, как в продукте: «API Kaiten», «External Webhooks», «Kaiten API Access».

### Чего избегать

- Восклицательных знаков и превосходных степеней («самый лучший», «революционный»).
- Кликбейта и обещаний, не подкрепленных фактами.
- Канцелярита и пассивных конструкций.
- Длинных сложноподчиненных предложений.
- Жаргона без расшифровки — если термин может быть незнаком, дается короткое пояснение или ссылка.

## 5. Тон для технических анонсов (API, вебхуки, дополнения)

Для анонсов, адресованных разработчикам, действуют те же правила плюс:

- Код и методы оформляются **моноширинным шрифтом**: `api.authorize()`, `const api = context.getApiClient()`.
- Кратко поясняется назначение каждого метода/параметра.
- Даются ссылки на портал разработчиков (developers.kaiten.ru) и конкретные разделы документации.
- Практическая польза все равно на первом месте: сначала «что это дает» (сценарии), потом технические детали.
- Важные предупреждения (например, «секрет показывается один раз») выносятся в отдельный акцентный блок со списком.
